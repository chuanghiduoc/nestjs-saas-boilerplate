# 0013 - Build toolchain: ESM + SWC, TS7 type-check / TS6 tool API, Vitest, oxlint, pnpm supply-chain policy

- Status: accepted
- Date: 2026-09-25

## Context

Sub-project 1 needs the first, foundational toolchain for the whole boilerplate:
module system, build (S1), type-check strategy (S2), test runner with a proof
that decorator-based DI metadata survives the build (S3), lint/format, and a
package-installation policy that resists supply-chain compromise. This ADR
records the decisions and, per the task's controller rulings, every place
reality diverged from the task brief and why.

## Decision

- **Module system:** ESM (`"type": "module"` in package.json), internal imports
  use explicit `.js` extensions (as generated by the Nest schematic and
  verified in `src/main.ts`).
- **Build:** SWC via `nest build` (`nest-cli.json` → `compilerOptions.builder:
  "swc"`, `typeCheck: false`, `sourceRoot: "src"`), configured by a hand-written
  `.swcrc`. No CommonJS fallback was needed — S1 succeeded on the first try
  including running the compiled ESM output directly with `node dist/main.js`.
- **Type-check:** TypeScript 7 (`typescript@7.0.2`) under the `ts7` alias,
  invoked as `node node_modules/ts7/bin/tsc --noEmit -p tsconfig.json` via the
  `typecheck` script. The plain `typescript` devDependency stays on the 6.x
  line (6.0.3) for tool APIs (`@swc-node/register`, and later
  `dependency-cruiser`), because TS7 does not yet expose a compiler API those
  tools require, and `@swc-node/register`'s own `peerDependencies` pin
  `typescript: ">= 4.3 < 7"` — it would refuse TS7 anyway.
- **Test runner:** Vitest 5 + `unplugin-swc` (so decorator metadata is emitted
  the same way in tests as in the SWC build), with a single `vitest.config.ts`
  using `test.projects` (`unit` → `test/unit/**/*.spec.ts`, `integration` →
  `test/integration/**/*.spec.ts` + `test/e2e/**/*.spec.ts`, with
  `globalSetup`, longer timeouts, and `fileParallelism: false`). `@swc-node/register`
  is kept as a devDependency for `pnpm env:example`-style dev scripts and for
  child processes spawned by integration/e2e tests (Task 18/19), since Node's
  built-in type-stripping does not run decorators or map `.js` specifiers to
  `.ts` files.
- **Lint/format:** oxlint (type-aware, via `oxlint-tsgolint`) + prettier.
  `"lint": "oxlint --type-aware src/ test/ && prettier --check ."`,
  `"format": "prettier --write ."`.
- **Package policy (pnpm, written to `pnpm-workspace.yaml`):**
  `saveExact: true`, `minimumReleaseAge: 1440` (minutes), and an `allowBuilds`
  map allow-listing `@swc/core`, `msgpackr-extract`, `protobufjs` and
  explicitly denying `@scarf/scarf` — see "Deviation: `onlyBuiltDependencies` →
  `allowBuilds`" below for why the key name differs from the brief.
- **Consequence:** the Nest CLI's Swagger plugin (`nest-cli.json` →
  `compilerOptions.plugins: ["@nestjs/swagger"]`) is **not** enabled, because
  it only works with the default `tsc`/`swc`-metadata pipeline in a way that
  hasn't been validated against this ESM+SWC+TS7 combination yet; Swagger
  wiring is deferred to the HTTP sub-project task that actually adds
  `@nestjs/swagger`.

### Deviation: `onlyBuiltDependencies` → `allowBuilds`

The brief's Step 4 names `onlyBuiltDependencies` as the build-script allow-list
key. On the installed pnpm (11.23.0), that key **does not exist**. Per the
pnpm v11.0.0 release notes (`github.com/pnpm/pnpm/releases/tag/v11.0.0`):

> Removed deprecated build dependency settings: `onlyBuiltDependencies`,
> `onlyBuiltDependenciesFile`, `neverBuiltDependencies`,
> `ignoredBuiltDependencies`, and `ignoreDepScripts` [...] replaced by the
> `allowBuilds` setting, a mapping where package name patterns correspond to
> boolean values indicating whether build scripts are permitted to execute.

The same release also changed pnpm's own default: `minimumReleaseAge` now
defaults to `1440` (1 day) since pnpm v11 (previously `0`). We still set it
explicitly in `pnpm-workspace.yaml` for clarity and to not depend on an
implicit default.

`pnpm-workspace.yaml` (final):

```yaml
minimumReleaseAge: 1440
saveExact: true

allowBuilds:
  "@swc/core": true
  msgpackr-extract: true
  protobufjs: true
  "@scarf/scarf": false
```

`strictDepBuilds` (default `true`) and `dangerouslyAllowAllBuilds` (default
`false`) were left at their pnpm defaults, which is exactly the "block
everything not explicitly allowed" posture the brief asked for.

### Deviation: CLI already scaffolds Vitest + oxlint, not Jest + ESLint

The brief's Steps 7 and 9 assume `nest new` generates Jest and ESLint that
must be removed. With `@nestjs/schematics` `^12.0.0` (resolved `12.0.5`), the
generator now scaffolds **Vitest** (`vitest.config.ts`, `vitest.config.e2e.ts`,
`"test": "vitest run"`, no `jest` block in `package.json`, no
`test/jest-e2e.json`) and **oxlint** (`.oxlintrc.json`,
`"lint": "oxlint --type-aware src/ test/"`) directly — there was no Jest or
ESLint to remove (`pnpm list eslint oxlint prettier` shows only `oxlint` and
`prettier`). Consequently:

- The "remove jest/ts-jest/@types/jest" part of Step 7 was a no-op; we still
  reinstalled `vitest`, `@vitest/coverage-v8`, `@nestjs/testing`, `supertest`
  under our own `saveExact` policy (the scaffold had installed them with `^`
  ranges before we set `saveExact`), and added `unplugin-swc` and
  `@swc-node/register`, which the scaffold does not include.
- We replaced the scaffold's default `vitest.config.ts` /
  `vitest.config.e2e.ts` pair with the brief's single `vitest.config.ts` using
  `test.projects` (verified against `vitest.dev/guide/projects`: inline
  `projects` is the current, non-deprecated mechanism — `vitest.workspace.ts`
  is what's deprecated since 3.2 — and `extends: true` is vitest 5's default
  for inline projects, kept explicit for clarity). We deleted
  `vitest.config.e2e.ts` since it's superseded by the `integration` project.
- We deleted the CLI-generated `src/app.controller.spec.ts` and
  `test/app.e2e-spec.ts`: both used Vitest's `globals: true` API (bare
  `describe`/`it`/`expect`), which our config turns off

  would have left dead, never-executed test files. `test/app.e2e-spec.ts` also
  had a real type bug independent of this decision — see next section.
- We kept the CLI's `oxlint --type-aware` flag in the `lint` script (a
  stronger default than the brief's plain `oxlint`) and appended
  `&& prettier --check .` per the brief.

## Alternatives considered

- **CommonJS instead of ESM (S1 fallback):** not needed — SWC + ESM worked on
  the first attempt, including running the compiled output directly with
  `node dist/main.js` and via `nest start`.
- **Single TypeScript version instead of TS7/TS6 split:** rejected — TS7 has
  no compiler API yet, and `@swc-node/register`'s peer range (`>= 4.3 < 7`)
  actively rejects TS7. The two-alias approach isolates "TS7 for
  `--noEmit` type-checking" from "TS6 for anything needing the compiler API"
  without version conflicts, since pnpm resolves `typescript` (plain,
  consumed by tools) and `ts7` (aliased, consumed only by our `typecheck`
  script) as fully independent installs.
- **`nest new`-generated Jest/ESLint kept as-is:** moot — the generator no
  longer produces them; see "Deviation" above.

## Consequences

- Every later task can rely on: `pnpm build` (SWC, ESM, `dist/main.js` +
  future `dist/main.api.js` / `dist/main.worker.js` / `dist/main.migrate.js`
  once those entrypoints exist), `pnpm typecheck` (TS7, strict,
  `noUncheckedIndexedAccess`), `pnpm test` / `pnpm test:int` (Vitest projects),
  `pnpm lint` (oxlint type-aware + prettier check), `pnpm start:dev`.
- `pnpm test:int` is wired up (`vitest run --project integration`) but not
  exercised in this task — its `globalSetup: ['test/support/infra.global-setup.ts']`
  target does not exist yet. Docker/Testcontainers-backed integration tests
  are explicitly out of scope for this task per the controller's ruling; the
  file will be added when a task actually needs Postgres/Redis-backed tests.
- No Nest CLI Swagger plugin is enabled (see Decision).
- `docs/` is excluded from `prettier --check .` — future tasks that add
  Markdown under `docs/` should be aware formatting there is not enforced by
  this repo's lint gate.

## Fix round 1 (post-review)

Code review flagged two issues in the initial commit:

1. **`.oxlintrc.json` had `"typescript/no-explicit-any": "off"`.** This
   directly contradicts the Global Constraint "Không cast mù: không `as
   never`, không `any`", and Task 1 is what establishes the lint gate every
   later task runs against — leaving it off meant nothing in the toolchain
   enforced that constraint (TS `strict` only catches *implicit* `any`, not
   explicit `any` annotations). Fixed by changing the rule to `"error"` in
   `.oxlintrc.json`, keeping everything else in that CLI-generated file as
   is. Verified the rule actually fires (not just silently accepted) by
   writing a throwaway `src/__lint_sanity_check.ts` with
   `function bad(x: any): any`, confirming `oxlint --type-aware` reported two
   `typescript(no-explicit-any)` errors and exited 1, then deleting the
   scratch file and re-confirming `pnpm lint` passes clean on the real code.

2. **`devDependencies.typescript` was `^6.0.2`, a range, under a
   `saveExact: true` policy.** This range leaked in from the `nest new`
   scaffold, from before we ran `pnpm config set save-exact true`. Per the
   "no hand-edited versions" rule, this was fixed through pnpm, not by
   editing the string directly. Two attempts before landing on the right one,
   recorded here since the pnpm behaviour is non-obvious:
   - `pnpm add -D typescript@^6` — pnpm treats an explicit `^` in the
     specifier you type as intentional and preserves that operator in
     `package.json` (`saveExact` only normalizes specifiers that *you* leave
     unversioned/unranged). Result: still `^6.0.3` — not what we want.
   - `pnpm add -D typescript@6.0.3` (exact version, no operator) — this is
     the correct form: `6.0.3` is not an invented version, it is the same
     version that was already resolved and running (confirmed via
     `pnpm view typescript versions --json`, filtered to the `6.x` line:
     `6.0.3` is the newest published stable 6.x release; everything newer is
     either a `6.0.0-dev.*` prerelease or the `7.x` line). Because our ADR's
     own decision is "stay on TS6 for tool APIs, TS7 only under the `ts7`
     alias for type-checking", asking pnpm for exactly the version already in
     use — rather than an unqualified `pnpm add -D typescript` (which would
     jump to the `latest` dist-tag, `7.0.2`, breaking the TS6/TS7 split and
     `@swc-node/register`'s `typescript: ">= 4.3 < 7"` peer range) — is the
     correct way to let the package manager (not a hand edit) write the exact
     pin. `package.json` now has `"typescript": "6.0.3"`, matching
     `"ts7": "npm:typescript@7.0.2"` in style (both exact, both package-manager
     written).

   `pnpm list typescript ts7` after the fix confirms both resolve correctly:
   `typescript@6.0.3` (plain) and `ts7@npm:typescript@7.0.2` (alias).

Re-verification after both fixes: `pnpm lint`, `pnpm typecheck`, `pnpm test`,
`pnpm build` all pass — see the task report for the exact command output.

## Production image (Task 19, 2026-09-25)

One image for the three roles (spec 13.3): `Dockerfile` stages `deps` (`pnpm fetch`,
BuildKit cache mount) → `build` (`pnpm install`, `nest build`, `pnpm prune --prod`)
→ `runtime` (distroless, `USER 65532`, only `package.json`, production
`node_modules` and `dist/`). The role is the node argument list: `CMD` = api
(`--import ./dist/instrumentation.js dist/main.api.js`, same as `start:api`),
compose overrides it for `worker` and `migrate` (`dist/main.migrate.js up`).

Decisions:

- **Build base `node:24.21.0-trixie-slim`, not `bookworm-slim`.** The runtime
  `gcr.io/distroless/nodejs24-debian13` is Debian 13 (trixie); a trixie build
  stage keeps glibc identical between the stage that installs native
  dependencies and the one that loads them. Both images ship Node v24.21.0.
  The only native binary in the production tree is `msgpackr-extract`
  (prebuilt `@msgpackr-extract/msgpackr-extract-linux-x64`, N-API, glibc); no
  production dependency compiles from source.
- **pnpm pinned through `packageManager`** (`corepack use pnpm@11.23.0`, with
  sha512), so `corepack enable` in the image runs the exact pnpm that wrote the
  lockfile. `.npmrc` is never copied (none exists; `.dockerignore` blocks it).
- **`pnpm install --prefer-offline`**, not `--offline`: the `deps` layer can come
  from a layer cache (CI `type=gha`) while the store cache mount is empty;
  `--offline` would then fail, `--prefer-offline` downloads instead.
- **Declarations and source maps of dependencies are deleted** after the prune
  (`*.map`, `*.d.ts`, `*.d.mts`, `*.d.cts` under `node_modules`): never loaded at
  runtime, ~90 MB of the 212 MB production `node_modules`. Source maps of `dist/`
  are kept.
- **App files owned by root, not `--chown 65532`:** the process (UID 65532) can
  read but not modify its own code and dependencies (verified: writing to
  `/app/dist` fails with `EACCES`).
- **No `init: true` in compose / no tini:** node is PID 1 exactly as on
  Kubernetes. PID 1 gets no default signal actions, but `installShutdown`
  handles SIGTERM/SIGINT; the app spawns no child processes, so no zombie
  reaping is needed; health probes are `docker exec`'d and reaped by the shim.
  Side effect: a SIGTERM that arrives before `installShutdown` is registered
  (during boot) or to `migrate` (no handler) is ignored until the grace period
  ends and SIGKILL follows. `stop_grace_period: 30s` > `APP_SHUTDOWN_TIMEOUT_MS`
  (28 s).
- **Compose runtime hardening mirrors the Kubernetes settings of spec 13.3:**
  `read_only: true`, tmpfs `/tmp`, `cap_drop: [ALL]`, `no-new-privileges`.
  Container ports are pinned in compose (`HTTP_PORT=3000`,
  `WORKER_HEALTH_PORT=3001`) so port mapping and the `node -e fetch(...)`
  healthchecks always match; host ports come from `.env` and bind 127.0.0.1.

### Compose usage and secret split (Task 19 fix round 1)

- `pnpm env:example` writes two files. `.env.example` (→ `.env`) holds the app
  config and reaches the app containers through `env_file`. `.env.infra.example`
  (→ `.env.infra`, the `devInfra` namespace: superuser, `REDIS_PASSWORD`,
  role statement timeouts, host ports, `COMPOSE_REDIS_URL`) is used **only** for
  compose interpolation, so infra secrets never enter an app container by
  construction.
- Role passwords a service does not need are overridden to empty in its
  `environment` (config treats empty as missing): only `migrate` keeps
  `DB_OWNER_PASSWORD`, only `worker` keeps `DB_RELAY_PASSWORD`.
- The app services carry `profiles: [app]`, a `build` section (base images from
  `docker/images.env`) and `pull_policy: build`. Commands:
  - infra only (unchanged behaviour, `pnpm start:dev` keeps port 3000):
    `docker compose --env-file docker/images.env --env-file .env.infra --env-file .env up -d`
  - with the three app roles:
    `docker compose --env-file docker/images.env --env-file .env.infra --env-file .env --profile app up -d --build`
- `migrate` gets `stop_grace_period: 10m` (= default
  `DB_MIGRATION_STATEMENT_TIMEOUT_MS`): as PID 1 without a SIGTERM handler it
  ignores SIGTERM, and the running statement must finish before SIGKILL.

### GitHub Actions schedule exception (Task 20)

The nightly chaos workflow declares its cron directly in
`.github/workflows/nightly.yml`: `17 2 * * *` (02:17 UTC daily).
GitHub only reads CI schedules from workflow YAML; this is not application
configuration and cannot be supplied by the application Zod schema or an
environment variable. This is a scoped exception to the no-hardcoded-cron
constraint. Application schedules remain owned by their module config schemas.
The workflow also supports manual dispatch, runs on Ubuntu with Docker, and
builds before running the Testcontainers chaos suite, including Linux SIGTERM.
